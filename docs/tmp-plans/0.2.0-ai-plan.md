## Результат релиза

После выпуска `0.2.0` пользователь web-версии должен уметь:

1. Подключить собственный ключ OpenRouter и выбрать совместимую модель.
2. Открыть глобальный сворачиваемый ИИ-чат с любого экрана, вести несколько
   разговоров и получать потоковые ответы.
3. Выделить текст в reader и передать его в чат с собственным вопросом либо
   быстрой командой «Объясни проще» или «Кратко перескажи».
4. Создать сохраненное саммари главы или материала и наблюдать durable
   выполнение задачи.
5. Поставить фоновую ИИ-задачу в очередь, выполнить ее внутренним provider либо
   оставить внешнему агенту.
6. Создать revocable MCP-подключение, подключить внешнего агента и дать ему
   возможность claim-ить задачи, получать только разрешенный контекст и
   возвращать типизированные результаты.
7. Создать сокращенный производный `.lum`-материал через ту же очередь и
   открыть его обычным reader после успешной валидации.

Релиз должен доказать главное архитектурное свойство: внутренний provider и
внешний MCP-агент используют один `AiTask`/`AiRun`/artifact contract, а
различается только исполнитель.

## Важная граница подписки

Канонические [`../vision.md`](../vision.md) и
[`../systems/ai.md`](../systems/ai.md) прямо относят встроенную подписку Lumi к
будущему и исключают ее из текущего implementation scope. Поэтому `0.2.0`
включает:

- BYOK через OpenRouter/OpenAI-compatible API;
- provider abstraction, пригодную для будущего hosted provider;
- capability и entitlement boundaries, через которые позже можно подключить
  подписку без изменения chat/task/artifact contracts.

`0.2.0` не включает:

- платежи, тарифы, пробный период и управление подпиской;
- общий ключ Lumi или расходование серверного бюджета от имени пользователей;
- квоты, биллинг, возвраты, налоги и provider retention policy для hosted AI.

Если подписка должна войти именно в `0.2.0`, сначала требуется отдельное
продуктовое решение и обновление `vision.md`, `ai.md`,
`security-privacy.md`, account lifecycle и deployment/runbook документов.
До этого «взять подписку» и другие недействующие subscription controls
показывать в production UI нельзя.

## Текущее состояние и разрыв

На старте работы репозиторий содержит S1 Web Reader:

- общие доменные модели находятся в `crates/lumi-core`;
- Axum API и PostgreSQL persistence находятся в `crates/lumi-server`;
- Dioxus Web shell и reader находятся в `apps/web`;
- import jobs уже имеют durable status, retry, cancellation, atomic claim,
  lease и recovery;
- server-side secret storage уже используется для Telegram token;
- source-backed anchors, normalized packages, PDF text layer, Markdown и
  `.lum` import уже реализованы;
- Playwright проверяет основные browser flows.

Подготовительная часть `0.2.0` уже выполнена:

- приняты ADR 0019–0024 и закрыты Stage 0 spikes;
- добавлены AI/MCP domain types, validators и schema marker;
- опубликованы HTTP/MCP snapshots, fixtures и deterministic mocks;
- подготовлены отдельные AI/MCP router contributions.

Для production AI-среза пока отсутствуют:

- общий job runtime, пригодный не только для import;
- provider settings и account-scoped provider credentials;
- OpenRouter adapter;
- explicit source context/context pack implementation;
- conversations, messages, generations и streaming transport;
- AI tasks, runs, artifacts, summaries и derived-material relationship;
- queue UI;
- MCP token, transport и tools;
- selection-to-chat wiring;
- production observability, security и compatibility evidence поверх frozen
  fixtures.

После сверки repository state A1 закрыт и подтверждён commit trailer
`Lumi-Plan-Stage: 0.2.0/A1`. Product AI capabilities по-прежнему выключены:
следующая точка реализации — эпик E1, начинающийся с внутренних workstreams
A2/A3/B1/B2, а не повторный design, contract freeze или A1.

## Scope и non-goals

### В scope `0.2.0`

- cloud-backed web mode;
- один BYOK provider: OpenRouter через OpenAI-compatible API;
- account-scoped provider settings и один активный credential на provider;
- global chat и explicit context attachments;
- reader selection actions;
- сохраненные `brief`/`outline` саммари главы и материала;
- durable queue, bulk execute, cancellation, retry и recovery;
- типизированный `SummaryArtifact` и расширяемый общий artifact contract;
- abridged `.lum` material;
- AI-oriented MCP vertical slice и операции над уже реализованными
  materials/annotations, необходимые агенту для выполнения задач;
- capability discovery и fail-closed поведение;
- web E2E, PostgreSQL integration, MCP contract и security tests.

### Не входят в `0.2.0`

- встроенная платная подписка Lumi;
- OpenAI, Anthropic и другие provider-specific adapters;
- локальные модели и client-local execution;
- native desktop/mobile UI;
- voice transcription, cards, questions, entity graph и explain-back UI;
- автоматический запуск всех queued tasks при появлении ключа;
- agent UI или agent conversation внутри Lumi chat;
- доступ MCP к credentials, admin, billing, chat runtime или account deletion;
- сложная MCP grant/audit platform, per-tool scopes и schema registry;
- branching, sharing, folders и pinning разговоров;
- автоматическая перегенерация результатов при новой source revision;
- Tantivy/fastText, global search surface и library-wide ranked retrieval.

Контракты не должны блокировать перечисленные будущие сценарии. В частности,
task kind, artifact kind и provider kind являются расширяемыми enum/string
contracts с проверкой поддерживаемых capabilities.

## Инварианты реализации

1. Chat turn никогда не создает `AiTask` автоматически.
2. Любая неинтерактивная AI operation сначала создает durable `AiTask`.
3. `Выполнить сейчас` создает ту же task, затем атомарно передает ее
   внутреннему worker.
4. Internal worker и MCP agent конкурируют за один atomic claim; двойная
   публикация результата невозможна.
5. Provider credential никогда не возвращается клиенту после сохранения, не
   попадает в sync, logs, diagnostics или MCP.
6. Контекст из Lumi передается явно и ограниченно. Вся библиотека не становится
   скрытым prompt context.
7. Любой source-backed результат содержит revision и anchors/citations,
   использованные при генерации.
8. Structured output проходит schema validation до публикации artifact.
9. Пользовательские правки не перезаписываются новой генерацией молча.
10. MCP вызывает те же application services, что и HTTP/Web, и не содержит
    дублирующей бизнес-логики.
11. Raw chat messages не попадают в Desk и search автоматически. Туда попадают
    только явно сохраненные typed artifacts.
12. Частично созданный abridged package не становится видимым материалом.

## Целевая архитектура

```text
Reader / Library / Global Chat / AI Queue
                 |
                 v
       Axum /api/v1 application boundary
                 |
       +---------+------------------+
       |                            |
       v                            v
ChatApplicationService      AiTaskApplicationService
       |                            |
       v                            v
ContextPackBuilder          Common Job Runtime
       |                     /              \
       v                    v                v
AiProviderClient     OpenRouter worker    MCP agent
       |                    \                /
       v                     v              v
Streaming response        validated typed result
                                  |
                         Artifact / Derived Material

External agent -> /mcp -> MCP adapters -> same application services
```

`lumi-core` владеет platform-independent contracts. `lumi-server` владеет
persistence, provider calls, secret storage, queue execution, MCP transport и
access checks. `lumi-web` владеет presentation, но не хранит authoritative
conversation/task state.

## Решения, обязательные до основного кода

### ADR

До изменения schema должны быть приняты:

1. **AI task/artifact schema.** Сущности, status machines, schema version,
   idempotency, active summary uniqueness, source revision и sync impact.
2. **Common Job Runtime.** Как import и AI используют общие leases, recovery,
   retry, cancellation и diagnostics без рискованного одномоментного
   переписывания import pipeline.
3. **Provider secrets.** Account scope, encryption key version, rotation,
   fingerprint, deletion и redaction.
4. **Explicit source context contract.** `SourceContextResolver`,
   `AiContextPack`, source ref/citation format, permission snapshot, limits и
   invalidation без зависимости от search index.
5. **MCP transport/auth/tools.** Transport profile, bearer token storage,
   revocation, request limits, tool schemas и claim fencing.
6. **Derived material provenance.** Связь abridged material с исходными
   `Material`, `DocumentRevision` и anchors; compatibility с `.lum`.

ADR не должны повторять этот план. Они фиксируют durable decisions,
compatibility impact, migration strategy, alternatives и required fixtures.

### Ограниченные spikes

Перед полной реализацией выполнить:

- Deep Chat в Dioxus Web: server-backed history, streaming, stop, reload,
  focus, keyboard, mobile-width и theme;
- OpenRouter adapter против локального mock server: streaming framing,
  structured output, cancellation, timeout и error mapping;
- MCP server transport с одним `get_lumi_capabilities` tool и revocable token;
- explicit source context на EPUB/Markdown/PDF: bounded sections, anchors и
  citations без search index;
- hierarchical summary одной большой fixture-книги;
- сборка generated `.lum` и повторный импорт через существующий pipeline.

Spike считается успешным только при наличии короткого отчета с решением
`adopt`, `adapt` или `reject`. Код spike не должен автоматически становиться
production architecture.

Если Deep Chat не проходит accessibility, reconnect или replaceability gates,
реализуется Dioxus-native message surface. Domain/API план при этом не
меняется.

## Domain contracts

### Provider

```text
AiProviderDescriptor {
  provider_kind
  display_name
  capabilities
  allowed_models
  credential_state
}

AiProviderClient {
  stream_chat(request) -> stream<AiProviderEvent>
  complete_structured(request, schema) -> AiProviderCompletion
  capabilities() -> ProviderCapabilities
}
```

В core не попадают OpenRouter-specific request/response types. Все
provider-specific options ограничиваются проверяемым `provider_options`.

### Task, run и claim

```text
AiTask {
  id
  user_id
  space_id
  kind
  source_scope
  instruction
  context_policy
  expected_result
  status
  priority
  idempotency_key
  active_dedupe_key
  created_by
  created_at
  updated_at
}

AiRun {
  id
  task_id
  executor_kind
  executor_ref
  status
  claim_id
  lease_expires_at
  attempt
  prompt_version
  schema_version
  model_info
  usage
  progress
  error
  started_at
  finished_at
}
```

Пользовательские task states:

```text
queued -> running -> succeeded
                 \-> needs_input
                 \-> failed
queued/running ----> cancelled
claim lease --------> queued | failed
```

`claimed` остается техническим состоянием run/lease. Внешние mutation tools
получают `claim_id`; progress/complete/fail/release принимаются только от
текущего claim. Heartbeat либо явное renew, либо разрешенное progress update
продлевает lease в пределах server policy.

### Context

```text
AiContextAttachment {
  kind
  object_id
  revision_id
  anchor_or_scope
  display_label
}

AiContextPack {
  id
  task_or_message_id
  policy_version
  source_refs[]
  chunks[]
  content_hash
  permission_snapshot
  created_at
}
```

Context pack содержит только разрешенный текст и metadata, необходимые
исполнителю. Secret, raw session data и недоступные annotations исключаются.
Для selection обязательны quote, anchor, surrounding blocks и material
metadata. Для большого material используется bounded section traversal и
hierarchical processing, а не один неограниченный prompt.

### Chat

```text
AiConversation {
  id
  user_id
  title
  active_model
  object_revision
  created_at
  updated_at
  deleted_at
}

AiMessage {
  id
  conversation_id
  role
  content
  attachments[]
  status
  created_at
}

AiGeneration {
  id
  conversation_id
  user_message_id
  assistant_message_id
  status
  provider
  model
  usage
  error
  started_at
  finished_at
}
```

Одна conversation может иметь не более одной активной generation в первой
версии. Regenerate создает новую generation attempt и новый assistant response,
не меняя уже отправленный user message.

### Artifacts и summaries

```text
AiArtifact {
  id
  task_id
  run_id
  kind
  schema_version
  payload
  source_refs
  status
  object_revision
  created_at
  updated_at
}

SummaryArtifact {
  artifact_id
  source_material_id
  source_revision_id
  scope_kind
  scope_ref
  form
  edited_by_user
  supersedes_artifact_id
}
```

В первом срезе как сохраняемый typed artifact поддерживается `summary`.
Объяснение выделения остается chat response. Остальные artifact kinds могут
быть распознаны capability layer, но не объявляются доступными.

Уникальность активного summary:

```text
account + source_revision + scope_kind + scope_ref
```

Новая generation сначала создает candidate. Если текущий результат не
редактировался пользователем, явное успешное действие может сделать candidate
активным сразу. Если есть ручные правки, UI требует сравнить и принять либо
отклонить candidate.

## PostgreSQL и migration strategy

Точный DDL определяется ADR, но schema должна покрыть:

- `ai_provider_credentials`;
- `ai_provider_preferences`;
- `ai_conversations`;
- `ai_messages`;
- `ai_message_attachments`;
- `ai_generations`;
- `ai_tasks`;
- `ai_runs`;
- `ai_context_packs`;
- `ai_artifacts`;
- `summary_artifacts`;
- `derived_material_relations`;
- `mcp_connections`;
- при необходимости общие `job_events`/`job_diagnostics`.

Обязательные database invariants:

- все content entities имеют `user_id`/`space_id` и owner-scoped indexes;
- credential ciphertext, nonce, key version и fingerprint отделены от display
  settings;
- plaintext credential не существует ни в одной таблице;
- один активный credential на `(user_id, provider_kind)`;
- один active summary на source scope;
- active task dedupe не допускает двух эквивалентных queued/running tasks;
- current claim обновляется условно по `task_id + claim_id + lease`;
- successful completion и artifact publication происходят в одной
  транзакции;
- conversation/message order детерминирован;
- source revision и source refs обязательны для source-backed outputs;
- MCP token хранится только как verifier/hash, а plaintext показывается один
  раз при создании;
- permanent credential/MCP revoke немедленно делает дальнейшие вызовы
  недействительными.

Миграции только forward. Existing `import_jobs` не переписываются одним
рискованным шагом. Сначала выделяются общие Rust interfaces и проверенные SQL
lease primitives, затем AI использует тот же runtime contract. Физическое
объединение job tables допускается только отдельным ADR и совместимой
backfill-миграцией.

Любое изменение AI task/artifact schema повышает domain schema marker и
получает compatibility tests согласно `quality.md`.

## HTTP API

Ниже приведен целевой route surface. Имена полей и exact payload закрепляются
OpenAPI/contract fixtures во время реализации.

### Provider settings

```text
GET    /api/v1/providers
GET    /api/v1/providers/openrouter
PUT    /api/v1/providers/openrouter/credential
DELETE /api/v1/providers/openrouter/credential
PATCH  /api/v1/providers/openrouter/preferences
POST   /api/v1/providers/openrouter/validate
```

`GET` возвращает только state, fingerprint, last validation и preferences.
`PUT` принимает credential один раз через HTTPS/same-origin authenticated
request, требует CSRF и не отражает secret в response.

### Conversations and streaming

```text
GET    /api/v1/ai/conversations
POST   /api/v1/ai/conversations
GET    /api/v1/ai/conversations/{conversation_id}
PATCH  /api/v1/ai/conversations/{conversation_id}
DELETE /api/v1/ai/conversations/{conversation_id}
POST   /api/v1/ai/conversations/{conversation_id}/messages
GET    /api/v1/ai/generations/{generation_id}/events
POST   /api/v1/ai/generations/{generation_id}/stop
POST   /api/v1/ai/generations/{generation_id}/retry
POST   /api/v1/ai/generations/{generation_id}/regenerate
```

Рабочее направление streaming transport — POST для durable message/generation
creation и отдельный authenticated SSE stream для событий. Spike обязан
проверить reconnect cursor, backpressure, cancellation и proxy buffering.
Если transport меняется, lifecycle и persistence contracts сохраняются.

### Tasks, queue and artifacts

```text
GET    /api/v1/ai/tasks
POST   /api/v1/ai/tasks
GET    /api/v1/ai/tasks/{task_id}
POST   /api/v1/ai/tasks/{task_id}/execute
POST   /api/v1/ai/tasks/{task_id}/cancel
POST   /api/v1/ai/tasks/{task_id}/retry
POST   /api/v1/ai/tasks/bulk-execute
GET    /api/v1/ai/artifacts/{artifact_id}
POST   /api/v1/ai/artifacts/{artifact_id}/accept
POST   /api/v1/ai/artifacts/{artifact_id}/reject
```

List routes используют cursor pagination. Creates/mutations требуют
`Idempotency-Key` там, где повтор запроса может создать duplicate work.

### Summaries

```text
GET    /api/v1/materials/{material_id}/summaries
POST   /api/v1/materials/{material_id}/summary-tasks
PATCH  /api/v1/ai/summaries/{summary_id}
DELETE /api/v1/ai/summaries/{summary_id}
POST   /api/v1/materials/{material_id}/abridgement-tasks
```

Summary create принимает source revision, `chapter | material`, scope ref,
`brief | outline` и execution mode `enqueue | execute_now`.

### MCP connections

```text
GET    /api/v1/mcp/connections
POST   /api/v1/mcp/connections
DELETE /api/v1/mcp/connections/{connection_id}
POST   /api/v1/mcp/connections/{connection_id}/rotate
```

Сам MCP endpoint остается под `/mcp`, а управление подключениями — обычным
account-scoped `/api/v1` surface. Plaintext token возвращается только в
create/rotate response.

## OpenRouter/BYOK implementation

### Credential flow

1. Пользователь открывает личные AI settings.
2. UI заранее объясняет, что выбранный context будет уходить внешнему provider.
3. Пользователь вводит ключ и выбирает default model.
4. Server выполняет bounded validation request.
5. При успехе key шифруется reusable secret store и сохраняется account-scoped.
6. UI получает только `configured`, fingerprint и validation status.
7. Delete удаляет credential и останавливает новые internal executions; уже
   claimed runs завершаются по явно выбранной cancellation policy.

Нужно обобщить существующий Telegram secret mechanism в reusable
`SecretStore`, не создавая второй несовместимый способ шифрования.
Master key не хранится в PostgreSQL. Ciphertext копируется backup-ом, а
операторский runbook обязан описать backup/restore/rotation key material.

### Provider errors

Нормализовать как минимум:

- invalid/revoked credential;
- model unavailable;
- rate limit;
- quota/credit exhausted;
- context too large;
- provider safety/policy rejection;
- timeout/network/TLS;
- malformed streaming event;
- invalid structured result;
- user cancellation.

Пользователь видит понятную причину и retry affordance. Logs содержат только
provider code, request id, timing и redacted diagnostics.

### Cost controls

- model allowlist или validated free-form model id;
- task-specific max input/output limits;
- bounded context pack;
- optional estimate до bulk execute;
- cancellation;
- usage metadata per run: input/output tokens и provider-reported cost, если
  она надежно доступна;
- никаких неограниченных автоматических retries для billable calls.

## Explicit source context и context packing

`0.2.0` реализует общий `SourceContextResolver`, но не search engine.

Минимальный release path:

1. Разрешить selection по authoritative source-backed anchor.
2. Выполнить детерминированный bounded traversal для chapter/material scope по
   `ReadingDocument` или PDF text layer.
3. Сохранить document revision, source refs, anchors, text hashes,
   heading/page metadata и permissions.
4. Добавить permission filtering до context pack, а не после provider call.
5. Дедуплицировать соседние или перекрывающиеся source sections.
6. Формировать citations, которые Web может открыть в reader.

Для selection используются quote и surrounding blocks. Для whole
chapter/material summary используется section traversal и hierarchical
synthesis. Открытый поиск по library/records, BM25, fastText и ranked
`RetrievedChunk[]` принадлежат `0.4.0`.

`ai-explicit-context` и `ai-retrieval` являются разными capabilities.
`0.2.0` публикует только первую. Контракты source refs/citations должны быть
совместимы с последующим indexed retrieval без зависимости от его runtime.

## Глобальный чат

### UX

На desktop-width web чат представляет собой global side panel. На узкой ширине
— drawer/sheet. В обоих случаях:

- chat trigger доступен из global shell;
- panel можно свернуть без потери active conversation, draft и generation;
- список разговоров позволяет создать, открыть, переименовать и удалить чат;
- message surface показывает streaming, stop, retry, regenerate и error;
- composer показывает context attachments до отправки и позволяет удалить их;
- source citation открывает material в reader на anchor;
- отсутствие credential ведет в provider settings, но не создает task;
- reload восстанавливает durable messages и корректно reconciles active/failed
  generation.

Draft composer text можно хранить как rebuildable per-conversation browser UI
state. Messages и generation status authoritative только на server.

### Deep Chat adapter

Если spike успешен:

- vendor component подключается через pinned dependency и подготовленный asset
  step;
- Dioxus adapter переводит события send/stop/input в Lumi commands;
- component получает готовые messages и stream events от Lumi API;
- credential и прямой provider endpoint component не видит;
- attachment row, citations, source navigation и Lumi errors остаются под
  контролем Dioxus;
- внутренний формат Deep Chat не попадает в core, API или PostgreSQL.

Нельзя строить critical locators на закрытых Shadow DOM details. Playwright
должен находить global chat, conversation controls, composer, stop и errors по
semantic roles/labels.

## Reader selection actions

Для reflowable reader и PDF text layer реализовать общий flow:

```text
selection
  -> normalize to source-backed Anchor
  -> choose action
  -> open global chat
  -> attach visible selection context
  -> prefill/submit instruction
```

Действия первого среза:

- `Спросить ИИ` — прикрепляет context, фокусирует пустой composer;
- `Объясни проще` — прикрепляет context и отправляет versioned instruction;
- `Кратко перескажи` — прикрепляет context и отправляет versioned instruction.

Selection context включает quote, anchor, surrounding blocks, material title,
chapter/page и revision. Если anchor устарел либо source text недоступен,
отправка блокируется с восстановимой ошибкой; нельзя молча отправлять другой
фрагмент.

Для scanned PDF без text/OCR action скрывается или объясняет необходимость
text layer. Visual crop/vision не входит в первый срез.

## Saved summaries

### Chapter/material workflow

```text
summary command
  -> idempotent AiTask
  -> internal claim or queued state
  -> source sections/context pack
  -> per-section generation
  -> synthesis
  -> citation/coverage validation
  -> SummaryArtifact candidate
  -> active summary
```

Reader показывает chapter action в конце главы. Material action доступен из
material details и в конце чтения.

UI состояния:

- summary отсутствует;
- queued;
- running с bounded progress;
- needs input;
- failed с причиной/retry;
- candidate ожидает принятия;
- active summary;
- source revision changed.

Default формы для release:

- chapter — `brief`;
- material — `outline`.

Это рабочий выбор плана. Если он сохраняется после UX-проверки, его нужно
перенести в `ai-summaries.md`.

Редактор summary обновляет content через `expected_revision` и ставит
`edited_by_user = true`. Последующая generation никогда не заменяет такой
summary без explicit accept.

### Abridged `.lum`

Workflow:

1. Зафиксировать исходную `DocumentRevision`.
2. Разбить material по spine/chapters.
3. Создать сокращенные chapter drafts с citations.
4. Выполнить synthesis, consistency и coverage checks.
5. Собрать strict `.lum` source project/package.
6. Прогнать существующие `.lum` validation/import stages.
7. В одной publication transaction создать derived `Material`,
   `DocumentRevision` и provenance relation.
8. Только после commit показать материал в library.

Повторная генерация создает новую revision derived material либо новый
candidate согласно ADR. Original material/revision не изменяется.

External agent может вернуть либо typed chapter/package inputs, либо bounded
upload reference на package. Большой `.lum` не передается inline через MCP.
Server всегда повторно валидирует package и permissions.

## AI task queue

### Web surface

Отдельная AI Queue page содержит:

- фильтры status/type/material;
- cursor-paginated table;
- type, target, status, created time, executor и progress;
- source link;
- single и bulk selection;
- `Выполнить сейчас`, cancel, retry и open result;
- безопасное скрытие завершенной задачи из рабочего представления без удаления
  artifact.

Browser не вызывает provider по одной task. Bulk execute — одна server command,
которая атомарно назначает доступные tasks internal worker и возвращает
per-task outcome.

### Job runtime

Из import pipeline извлекаются общие проверяемые primitives:

- atomic claim;
- claim fencing;
- lease/heartbeat;
- retry policy и attempt budget;
- cancellation flag;
- progress snapshot;
- restart recovery;
- redacted diagnostics;
- idempotent completion.

Они образуют один `Job` execution contract для typed kinds `import`, `ai`,
`transcription`, `search_index`, `material_fingerprint`, `export` и `delete`.
Доменные requests/status могут храниться в отдельных таблицах, но второй
claim/lease/retry/recovery engine запрещён.

AI-specific orchestration использует этот contract, но import semantics и
работающие recovery tests не ослабляются. Физическое объединение существующих
`import_jobs` с новой execution table не является условием релиза, если import
подключён через совместимый adapter и проходит общий runtime test suite.

Internal worker должен быть отдельной background execution loop внутри
server/worker process, а не spawned future, живущей только до конца HTTP
request. Production topology определяет, запускается ли loop в server binary
или отдельном worker mode; один и тот же task не должен быть claim-нут обоими.

## MCP agent integration

### Connection flow

1. Пользователь создает именованное connection.
2. Server показывает endpoint и token один раз.
3. Agent вызывает `get_lumi_capabilities`.
4. Все дальнейшие tools действуют как account user и проходят обычные access
   checks.
5. Пользователь видит список connections, fingerprint, created/last-used time и
   может revoke/rotate token.

Первый token дает обычный full product access аккаунта в пределах MCP
allowlist, как зафиксировано в `mcp.md`. Он не дает admin/system права и не
открывает исключенные операции.


Tool `search` добавляется позднее вместе с `SEARCH-005` и capability

Import/download/archive/restore/permanent delete входят в обязательный
вертикальный срез `0.2.0` и вызывают те же application services, что Web.
Permanent delete использует двухшаговый prepare/confirm contract.

### Queue worker protocol

- `list_ai_tasks` возвращает только claimable/account-owned tasks;
- `claim_ai_task` атомарен и возвращает opaque `claim_id`, lease expiry и
  expected result schema;
- `get_ai_task_context` проверяет current claim и context policy;
- progress update bounded, rate-limited и продлевает lease по policy;
- completion принимает typed result, claim id и idempotency key;
- server валидирует schema, source refs и output size;
- artifact publication и task success происходят транзакционно;
- повтор того же completion возвращает прежний outcome;
- stale claim получает conflict и не может опубликовать result;
- release возвращает task в queue без artifact;
- fail хранит redacted code/message и применяет retry policy.

Agent не получает BYOK и не вызывает Lumi chat runtime. Если ему нужен
интерактивный explain-back, он ведет его в собственном UI и возвращает
финальный typed result отдельной задачей; этот сценарий не объявляется
реализованным в `0.2.0`.

### Правила исполнения внутренних workstreams

- Каждый внутренний workstream доводится до локального gate вместе с tests и
  документацией; checkpoint ROADMAP закрывается только по outcome всего эпика.
- Timestamped migration создаётся только для активного этапа; уже принятую
  migration не переписывают.
- Frozen DTO меняются отдельным contract change с обновлением всех затронутых
  mocks и fixtures.
- Top-level `Cargo.toml`, `crates/lumi-server/src/lib.rs`,
  `apps/web/src/account.rs`, capabilities и `README.md` обновляются в том же
  этапе, которому это требуется.
- Capability включается только после готовности route, persistence, UI и
  минимального end-to-end evidence соответствующей возможности.

## Test strategy

### Domain/unit

- state transitions и запрещенные переходы;
- active task dedupe;
- claim lease/fencing;
- artifact schema validation;
- summary slot uniqueness и superseding;
- prompt/context version selection;
- citation/source ref validation;
- provider error mapping;
- capability calculations.

### PostgreSQL integration

- account isolation для каждого AI/MCP query;
- create/claim/heartbeat/complete/retry/cancel races;
- idempotent create и complete;
- restart recovery при queued/running/expired lease;
- atomic artifact publication;
- conversation ordering и generation reconciliation;
- manual edit vs new candidate;
- MCP revoke/rotate concurrency;
- forward migration с существующей S1 database.

### Provider contract

Локальный deterministic mock server должен уметь:

- отдавать обычный и chunked streaming response;
- разрывать stream;
- задерживать first token;
- возвращать 401, 429, 5xx и malformed JSON;
- превышать output limits;
- вернуть structured payload, не соответствующий schema;
- наблюдать cancellation.

CI и E2E не зависят от live OpenRouter и не используют реальный ключ.

### MCP contract/security

- capability discovery;
- schema validation каждого tool;
- cursor pagination и limits;
- missing/invalid/revoked token;
- cross-account ids;
- stale claim и duplicate completion;
- oversized context/result;
- forbidden credential/admin/chat operations;
- prompt-injection text не меняет MCP authorization;
- two-step destructive flow, если он входит в release.

### Browser E2E

- настройка/удаление mocked BYOK;
- create/switch/rename/delete chat;
- send/stream/stop/retry/reload;
- collapse chat при переходе library -> reader -> queue;
- reflowable и PDF selection -> ask/explain/summary;
- enqueue vs execute now;
- queue filter/bulk/cancel/retry/open result;
- chapter/material summary и manual edit candidate;
- MCP connection create/revoke без повторного показа token;
- abridged material появляется только после success.

Все критические controls имеют semantic role/label и доступны keyboard-only.

### Security

- plaintext secret scan PostgreSQL/logs/browser snapshots;
- CSRF для credential и MCP connection mutations;
- strict CORS/origin и HTTPS fail-closed;
- request/response size and timeout limits;
- malicious Markdown/HTML in model output;
- citation/anchor injection;
- provider/MCP error redaction;
- account authorization на каждом nested id;
- cancellation и resource exhaustion.

Model output Markdown проходит безопасный renderer/sanitizer. Модель не может
создать executable HTML/JS в chat, summary или generated `.lum`.

### Performance/reliability targets

Цели release regression suite, не публичный SLA:

- queue list: p95 менее 300 ms для 1 000 tasks без provider work;
- atomic claim: p95 менее 200 ms без contention;
- server streaming relay overhead: p95 менее 100 ms поверх provider latency;
- chat history first page: p95 менее 300 ms для 100 conversations;
- restart recovery не требует ручной правки database;
- UI остается responsive во время streaming и bulk execution;
- context и outputs всегда ограничены configured byte/token budgets.

Если эти targets сохраняются после релиза, их нужно перенести в
`quality.md`.

## Observability

Нужны metrics/traces:

- tasks по kind/status/executor;
- queue age и run duration;
- lease expiry/retry/cancel;
- provider latency до first token и total;
- normalized provider error class;
- input/output tokens и optional cost;
- context chunks/bytes без содержимого;
- artifact validation failures;
- active SSE connections/reconnects;
- MCP calls по tool/outcome, token fingerprint и account id;
- abridgement stage duration.

Запрещено логировать:

- prompts, quotes, messages и generated content по умолчанию;
- API keys, MCP tokens и auth cookies;
- raw context packs;
- full provider request/response bodies.

Для support diagnostics пользователь может отдельно экспортировать
санитизированный run report с ids, versions, timings и error codes.

## Deployment и operations

- добавить AI/MCP environment configuration без shared provider key;
- сохранить master secret material вне PostgreSQL и image;
- убедиться, что production proxy не buffer-ит AI SSE;
- определить worker concurrency и graceful shutdown;
- при shutdown перестать claim-ить новые tasks, отменить/освободить leases и
  корректно завершить streams;
- readiness проверяет schema и worker configuration, но не вызывает платный
  provider;
- backup/restore включает AI tables и согласованный secret key backup;
- self-hosted instance может полностью отключить AI/MCP capabilities;
- OpenRouter validation и runtime используют fixed provider base URL из
  server config, а не произвольный пользовательский URL, чтобы не добавить
  SSRF surface.

## Rollout

1. Применить forward migrations при выключенных AI capabilities.
2. Развернуть server с provider/MCP routes, но скрытым UI.
3. Прогнать mock-provider и MCP smoke на staging.
4. Включить BYOK settings для внутренних аккаунтов.
5. Включить queue/summaries, затем global chat/selection.
6. Включить MCP AI worker после security smoke.
7. Включить abridgement после `.lum` compatibility evidence.
8. Только после всех gates объявить feature ids в capabilities и выпустить
   `0.2.0`.

Rollback приложения не должен требовать rollback schema. Новые таблицы и
additive columns остаются неиспользуемыми старым binary. Если новый binary
успел создать AI state, downgrade не должен удалять его.

| Риск | Последствие | Снижение |
| --- | --- | --- |
| Утечка BYOK | Компрометация аккаунта provider | reusable secret store, no-read API, redaction tests, key rotation |
| Cross-account context | Утечка личного текста | permission filtering до context pack, owner-scoped SQL tests |
| Двойное выполнение task | Двойная стоимость и artifacts | atomic claim, lease fencing, idempotent completion |
| Prompt injection в книге | Агент делает запрещенное действие | content не меняет authorization, typed tools и server validation |
| Deep Chat ограничивает UX | Хрупкий UI и accessibility | ограниченный adapter и Dioxus-native fallback |
| Live provider нестабилен | Ошибки chat/tasks | normalized errors, retry budget, mock contracts, cancellation |
| Большая книга переполняет context | Стоимость/ошибка provider | hierarchical processing, bounded chunks и coverage validation |
| MCP слишком привилегирован | Массовое изменение данных | account scope, allowlist, revoke, idempotency, two-step destructive actions |
| AI schema рано стабилизирована | Дорогая compatibility migration | versioned prompts/schemas, ADR, fixtures, additive evolution |
| Abridgement публикует мусор | Плохой derived material | candidate workflow, `.lum` validation, atomic publication |
| Scope релиза слишком велик | Незавершенные поверхности | gates по вертикальным срезам, capabilities скрывают неполные функции |

## Критический путь

```text
ADR/spikes [done]
  -> Contract Freeze 1 [done]
  -> A1 persistence/runtime [done]
  -> E1 personal AI assistant
  -> E2 tasks and summaries
  -> E3 external agents through MCP
  -> E4 derived .lum and release
```

Вся цепочка является критическим путём. Эпик не считается закрытым только по
компиляции отдельного модуля: его outcome, gate, tests и обязательная
интеграционная проверка должны пройти до начала следующего эпика.

Если abridged `.lum` угрожает сроку всего релиза, его нельзя тихо убрать из
capabilities или считать частично готовым. Нужно либо сохранить C3 на
критическом пути, либо отдельным продуктовым решением изменить scope и
canonical `ai-summaries.md`.

## Что переносится после релиза

После стабилизации `0.2.0` отдельными планами развиваются:

от него должны быть перенесены в `docs/systems/`, ADR и runbooks.
