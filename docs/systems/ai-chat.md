# Глобальный ИИ-чат

Status: draft

## Контекст

Глобальный ИИ-чат — основная интерактивная точка общения пользователя с ИИ в
Lumi. Он не принадлежит только reader, библиотеке или базе знаний: чат доступен
с любого экрана, может быть свернут на любом клиенте и сохраняет активный
разговор при переходе между частями приложения.

Чат должен давать полноценный опыт обычного ИИ-чата, а не быть формой для одной
команды. Пользователь создает отдельные разговоры, ведет многошаговый диалог,
получает streaming-ответы и управляет циклом генерации. Особенность Lumi —
возможность явно передавать в разговор контекст из материалов, выделений,
заметок и других объектов приложения.

Этот документ рамочно фиксирует продуктовую роль и границы чата. Детальная
информационная архитектура, UI-состояния, команды, API и persistence model
будут проработаны отдельным проходом перед реализацией.

## Основные принципы

- **Глобальность.** Один chat surface доступен из library, reader, search, KB,
  learning и других экранов.
- **Сворачиваемость на всех клиентах.** Пользователь может убрать чат, не
  закрывая разговор и не теряя введенный текст или текущую генерацию.
- **Полноценный chat lifecycle.** Чат поддерживает управление разговорами и
  полный цикл ответа модели, а не только заранее заданные AI actions.
- **Явный контекст.** Lumi показывает, какие объекты переданы в разговор.
  Открытый экран или вся библиотека не становятся скрытым контекстом
  автоматически.
- **Source-backed ответы.** Когда ответ опирается на материалы Lumi, он должен
  по возможности содержать ссылки на исходные фрагменты и anchors.
- **Прямой provider.** Интерактивный чат внутри Lumi использует подключенный
  provider и BYOK. MCP предназначен для работы внешнего агента с Lumi и не
  встраивает agent UI в этот чат.
- **Вне очереди.** Сообщения и ответы чата не создают `AiTask` и не
  превращаются в фоновые задачи автоматически.
- **Общий контракт.** Web, desktop и mobile используют общие сущности
  разговоров, сообщений и переданного контекста; различается только platform
  presentation.

## Пользовательские сценарии

- Пользователь открывает чат с любого экрана, сворачивает его, продолжает
  работу и возвращается к тому же разговору.
- Пользователь создает новый чат, открывает предыдущий, переименовывает или
  удаляет ненужный разговор.
- Пользователь отправляет обычный вопрос без контекста Lumi и ведет
  многошаговый диалог с моделью.
- Пользователь выделяет текст в reader, выбирает «Спросить ИИ», видит
  прикрепленный фрагмент в composer и задает собственный вопрос.
- Пользователь выбирает «Объясни проще» или «Кратко перескажи»; Lumi передает
  выделение в чат и подставляет соответствующую инструкцию.
- Пользователь прикрепляет главу, материал, заметку, highlight, результат
  поиска или сохраненный AI artifact к существующему разговору.
- Пользователь просит краткое саммари выделения и оставляет ответ только в
  чате.
- Пользователь просит саммари главы или материала, после чего может сохранить
  результат как отдельный `SummaryArtifact`.
- Пользователь сохраняет полезный ответ как note, explanation, cards или другой
  типизированный artifact; только сохраненный объект появляется в Workspace.
- Пользователь останавливает генерацию, повторяет ответ после ошибки или просит
  модель ответить заново.

## Функциональные границы

### Chat surface

На всех клиентах чат имеет два устойчивых состояния:

- развернут и доступен для чтения/ввода;
- свернут, но разговор и его состояние продолжают существовать.

Конкретное представление зависит от платформы: side panel, drawer, sheet или
отдельная компактная поверхность. Требование сворачиваемости и сохранения
контекста одинаково для web, desktop и mobile.

### Управление чатами

Рамочный minimum полноценного chat experience:

- создать чат;
- показать список и открыть существующий чат;
- автоматически предложить название и разрешить переименование;
- удалить чат;
- сохранить историю сообщений;
- продолжить разговор после повторного открытия приложения.

Архивация, folders, pinning, branching и sharing разговоров могут быть
добавлены после отдельной UX-проработки.

### Цикл ответа модели

Чат должен поддерживать:

- отправку сообщения;
- streaming ответа;
- состояние ожидания и генерации;
- остановку генерации;
- retry после transport/provider error;
- повторную генерацию ответа;
- продолжение диалога с учетом истории;
- отображение недоступного provider или невалидного ключа;
- сохранение завершенных сообщений и корректное состояние незавершенного
  ответа после reconnect/reload.

Редактирование уже отправленных сообщений, ветвление разговора, выбор модели
для отдельного сообщения и tool-call UI будут уточнены в детальном дизайне.

### Передача контекста в чат

Контекст передается как явное вложение к пользовательскому сообщению. Рамочно
поддерживаются:

- выделенный текст и его anchor;
- блок, раздел или глава;
- весь материал;
- highlight или note;
- результат поиска;
- KB note или принятый AI artifact;
- явно выбранный файл или другой поддерживаемый объект.

Composer показывает прикрепленные объекты до отправки и позволяет удалить
каждый из них. Для reader selection основной поток выглядит так:

```text
selection
  -> contextual action
  -> открыть глобальный чат
  -> прикрепить selection context
  -> собственный вопрос или быстрая инструкция
  -> отправить сообщение
```

Быстрая команда может отправить заранее понятную инструкцию сразу, если
действие однозначно. Команда «Спросить ИИ» только переносит контекст и оставляет
пользователю возможность сформулировать вопрос.

Перед отправкой Lumi формирует разрешенный context pack: quote, surrounding
blocks, material metadata и source refs. Большой объект, например книга или
библиотека, подключается через retrieval, а не целиком помещается в каждый
prompt.

### Саммари в чате

Короткое саммари выделения является обычным ответом в разговоре. Оно не обязано
создавать отдельный artifact.

Саммари главы или материала можно оставить в чате либо сохранить как
`SummaryArtifact`. Создание сокращенной версии книги или другого материала
является отдельной фоновой операцией: результат становится производным
материалом, а не просто длинным сообщением.

### MCP boundary

MCP не является частью chat runtime. Внешний агент подключается к Lumi извне,
может читать доступные ему данные, выполнять пользовательские операции и
обрабатывать AI task queue. Если агент ведет собственный интерактивный диалог,
этот диалог остается в интерфейсе агента; в Lumi возвращаются созданные объекты,
изменения или результаты задач.

Если direct provider/key недоступен или ответ модели не помог, chat flow
заканчивается ошибкой либо обычным ответом. Lumi не создает queued task
автоматически. Пользователь может отдельно перейти к фоновому действию, которое
создаст `AiTask` по контракту [`ai-task-queue.md`](ai-task-queue.md).

## Направление реализации UI

Целевая архитектура чата остается частью Dioxus/Axum-приложения Lumi. Для
сокращения объема первой реализации используем
[Deep Chat](https://deepchat.dev/) как заменяемый Web Component внутри Dioxus,
а не как отдельную архитектуру или владельца chat state.

Граница ответственности:

- **Dioxus shell** владеет глобальной панелью, сворачиванием, responsive
  presentation, списком чатов, переключением разговоров и передачей контекста
  из экранов Lumi.
- **Deep Chat adapter** дает message surface, базовый composer, scrolling,
  Markdown rendering, streaming display и низкоуровневые события
  send/stop/input.
- **Lumi chat state** владеет сообщениями, generations, context attachments,
  retry/regenerate semantics и состоянием активного разговора.
- **Axum backend** является источником истины для persistence, provider calls,
  server-side BYOK, streaming transport и access checks.

Deep Chat подключается только к API Lumi. Он не вызывает AI provider напрямую,
не получает BYOK credential и не использует browser storage как authoritative
conversation store. История загружается из Lumi, а события Web Component
преобразуются адаптером в доменные команды чата.

Context attachments и Lumi-specific actions остаются под контролем Dioxus.
Если их нельзя надежно встроить в composer Deep Chat, они отображаются как
отдельная строка attachments рядом с ним. Source citations и переходы к
anchors также являются функцией Lumi; Deep Chat используется для их
отображения только там, где это не требует хрупкой зависимости от внутреннего
Shadow DOM.

Такой подход намеренно оставляет путь к полностью Dioxus-native message
surface. Замена Deep Chat не должна менять `AiConversation`, `AiMessage`,
`AiContextAttachment`, API или server-side generation lifecycle.

Перед полной реализацией нужен ограниченный spike, который проверит:

- работу Web Component в Dioxus Web и целевых WebView-клиентах;
- streaming, stop и восстановление после reload;
- загрузку server-backed history и переключение чатов;
- передачу selection context из reader;
- rendering Markdown, citations и ошибок;
- theming, focus management, keyboard navigation и mobile layout;
- возможность заменить Deep Chat без утечки его формата в domain/API.

## Данные

Рамочно чат использует сущности из [`ai.md`](ai.md):

- `AiConversation` — отдельный чат;
- `AiMessage` — пользовательское, assistant или system/tool сообщение;
- `AiContextAttachment` — явно переданный объект Lumi и его source refs;
- `AiGeneration` — состояние конкретной попытки ответа модели.

Точная схема, правила удаления, reconnect и синхронизации будут определены в
детальном design/implementation плане.

## Privacy и provider

- Для текущего web scope BYOK credential хранится в защищенном server-side
  secret storage.
- Пользователь видит переданный в сообщение контекст до отправки.
- Lumi не добавляет всю библиотеку в prompt только потому, что чат открыт
  глобально.
- Ответы и контекст разговора приватны, пока пользователь явно не сохраняет или
  не публикует производный объект.
- Встроенная подписка Lumi не входит в текущий scope.

## Интеграции

- **Reader.** Передает selection, anchor, соседние блоки и быстрые команды.
- **Search.** Собирает bounded retrieval context для главы, материала,
  библиотеки и связанных заметок.
- **AI core.** Управляет provider, streaming, conversations и generations.
- **Очередь задач.** Не участвует в chat turns; пользователь запускает
  background action отдельно.
- **Artifacts/KB.** Позволяет сохранить полезный ответ или запустить создание
  отдельного типизированного результата.
- **Workspace.** Raw conversations/messages не входят в Workspace. Явно
  сохраненные notes и typed artifacts появляются там по material/source refs.
- **Синхронизация.** Сохраняет разговоры и сообщения между клиентами; provider
  secrets не входят в обычный plaintext sync.

## Альтернативы

- `accepted`: Dioxus/Axum владеют chat architecture, а Deep Chat используется
  как заменяемый UI-ускоритель первой реализации.
- `rejected`: React island с assistant-ui. Второй UI runtime и bridge не
  соответствуют выбранному направлению.
- `rejected`: OpenAI ChatKit как фундамент чата. Готовый Web Component
  привлекателен, но создает лишнюю зависимость от жизненного цикла, runtime и
  инфраструктурных решений OpenAI.
- `revisit`: полностью Dioxus-native message surface после стабилизации
  доменных контрактов и проверки ограничений Deep Chat.

## Открытые вопросы для детального прохода

- Информационная архитектура списка чатов и развернутой поверхности на каждой
  платформе.
- Семантика редактирования сообщения, regeneration и будущего branching.
- Выбор provider/model на уровне настроек, чата или отдельного запроса.
- UI цитат, context attachments, retrieval progress и provider/tool errors.
- Правила хранения незавершенного streaming-ответа после disconnect.
- Нужно ли индексировать историю разговоров или только явно сохраненные ответы.
- Какие части Deep Chat можно безопасно кастомизировать без зависимости от его
  внутренних Shadow DOM details?
